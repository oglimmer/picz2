## Architecture in one sentence

Backend runs as `api` and `worker` pods sharing the same JAR (different `SPRING_PROFILES_ACTIVE`); they share state via MariaDB + MinIO only; the worker drains a `processing_jobs` table via `SELECT … FOR UPDATE SKIP LOCKED`; TUS uploads go through a separate `tusd` Deployment that hooks back into the api on finish; a nightly retention CronJob (same JAR, `retention` profile) sweeps aged originals + TUS leftovers + orphan keys.

## Things to know before changing code

- **Profile gating is load-bearing.** Both pods boot the same JAR; misclassifying a `@Profile`-gated bean leads to one pod crashing on startup. Check both `Profiles.API` and `Profiles.WORKER` when adding services.
- **Storage keys are deterministic** (derived from asset id in `StoragePaths`). No path-drift recovery code is needed because paths can't drift.
- **Adding a new background operation** = add to `JobType` enum → worker method on `FileProcessingService` → switch case in `JobDispatcher` → api enqueue method on `FileStorageService` → controller endpoint returning 202. Mirror `REGEN_THUMBNAILS` or `ROTATE_LEFT`.
- **Rotate and enhance rewrite the original in place** (D17, D81). `ROTATE_LEFT` and `ENHANCE` share one worker flow (`FileProcessingService.rewriteOriginalAndRegenerate`) and one api gate (`FileStorageService.requireRewritableImage`): PUT over the `originals/` key, rebuild derivatives, new `publicToken`. There is no copy of the previous bytes, so neither can be undone, and a second enhance compounds on the first. A new in-place edit goes through the same two methods. **A single photo's enhance is look-first in both clients** (D82), a selection is enhanced directly after a confirm, like rotate and delete: `POST /api/files/{id}/enhance-preview` builds `derivatives/{id}/enhance-preview.jpg` at LARGE size without touching the row; the client shows it against the current picture and then calls `POST …/enhance` (accept) or `DELETE …/enhance-preview` (decline). The preview key is not a column: `deleteS3Objects`, the album bulk delete and the ENHANCE job remove it, `purgeOrphanedS3Objects` skips it. Serve it only through the owner-gated `GET /api/files/{id}/enhance-preview`, never through `/api/i/{token}`.
- **An enhanced photo is marked and skipped in bulk** (D83). The worker stamps `file_metadata.enhanced_at` inside the TX that commits the ENHANCE rewrite — rotate shares `rewriteOriginalAndRegenerate` and must not stamp, and `ENHANCE_PREVIEW` must not either. It reaches both clients as `FileInfo.enhancedAt`. A bulk enhance drops already-enhanced photos the way it drops videos (web `selectedEnhanceableIds`, iOS `selectedEnhanceablePhotos`); a single photo may still be enhanced twice after a warning. There is no server gate and no backfill: rows enhanced before V53 read as never enhanced.
- **Retention is irreversible** (`RetentionService` deletes S3 originals + nulls `file_path`). If you change retention logic, set `retention.dryRun: true` for one nightly cycle and read the log first.
- **All backwards-compatibility shims have been removed** (Phase 4e R3, 2026-04-30; the local-disk storage mode followed on 2026-09-05, D77). Object storage is the only storage: `ObjectStorageService` is a required bean, `file.upload.upload-dir` is scratch space only. Don't reintroduce a disk path for hypothetical future flexibility.
- **`hidden` is a privacy boundary, not a filter.** New uploads get the tag named by `users.new_asset_tag` (D70), which defaults to `hidden`. Anything carrying `hidden` must stay out of every public path: the share-token listing, the public single-image page and subscription mails all drop it. `/api/i/{token}` is deliberately NOT gated — the owner's own clients fetch pixels through it — so never hand a hidden asset's `publicToken` to an unauthenticated caller.
- **`hidden` is derived, not assigned** (D79). A photo carries it exactly while it has no other tag. Every tag edit in `FileStorageService` (single and bulk) and `TagService.deleteTag` keeps that true: adding a real tag drops `hidden`, losing the last one puts it back. Adding `hidden` by hand, or removing a lone one, is a 400. If you add a new way to change a photo's tags, route it through those methods or mirror the rule. Clients never list `hidden` as a toggle, only as a filter. There is no data migration on purpose: older rows keep their state until touched.
- **The browser never holds the password** (D78). The web app logs in once with Basic at `POST /api/auth/sessions`, keeps the returned `zst_…` session token in `localStorage`, and sends `Authorization: Bearer` from then on. `SessionTokenAuthenticationFilter` runs ahead of Basic; iOS and curl keep using Basic. A password change revokes every session and every upload token — keep it that way.
- **`/api/admin/**` needs `ROLE_ADMIN`** (D74), granted from `users.is_admin` in `CustomUserDetailsService`. Everyone else is `ROLE_USER`. Grant admin with SQL, never through an endpoint. `PUT /api/settings/languages/*` is admin-only too (D75): the two language names are one instance-wide pair.
- **`JobStatus` has no `FAILED`** (D76, V51). A failed attempt goes back to `QUEUED`; out of attempts means `DEAD_LETTER`. Don't reintroduce it.
- **The "storage full" banner is server-decided** (D80). `GET /api/storage-usage` returns `full` from `StorageQuotaService.Usage.isFull()`; the web (`useStorageUsage` + `StorageFullBanner.vue`) and iOS (`StorageUsageMonitor` + `StorageFullBanner`) show a non-dismissable banner exactly while it is true. Don't re-derive "full" from the numbers in a client, don't add a close button, and if you add a new way to change stored bytes, call the client's refresh after it.
- **The album shelf order is hand-made and server-side** (D84). `GET /api/albums` sorts by `albums.display_order`, id as tiebreaker; `PUT /api/albums/reorder` (`AlbumService.reorderAlbums`) renumbers from the posted list's index and answers with the whole shelf. Both clients drag a tile onto another tile, show the new order at once and then replace their list from the response — the server appends any album the caller did not mention, so never trust the list you sent. Web: `useAlbumShelfOrder` + `AlbumCard`'s drag props. iOS: a Reorder toolbar toggle, then `.draggable`/`.dropDestination` over `AlbumsViewModel.moveAlbum(draggedId:onto:)` — the tile's long press belongs to the context menu, so drag has to be a mode. No migration and no backfill: rows predating the first drag all carry 0 and fall back to id order.
- **A text card is a `file_metadata` row whose mime type keeps it out of every image path** (D86). A text card is an album entry with a headline and optional body text instead of pixels — a chapter heading. It is an ordinary row: `display_order`, `album_id`, tags, delete and the share listing all work unchanged. What makes it a card is `mime_type = application/x-picz-text-card`; because every sweep, cover picker and rewrite gate already narrows on `image/%` or `video/%`, a card is skipped by all of them with **no new condition** — thumbnails, transcode, EXIF, GPS, album cover, rotate, enhance. Retention skips it on the null `file_path`. So if you add a new background operation, narrow it on the mime family the way the others do, and it will step over cards for free. There is deliberately **no `kind` column** (`V54` adds only `headline` and `body_text`): `FileInfo.kind` is derived in `FileInfoMapper`, and the clients switch on that rather than sniffing the type. The row is `DONE` on insert and no job is enqueued — a card left at `QUEUED` spins forever in both clients. It gets the user's new-asset tag like an upload, which is what keeps D79 true. `POST /api/files/text-cards` creates, `PUT /api/files/{id}/text-card` edits (a photo id is a 400); `GET /api/i/{token}` 404s for a card. The background is the **next** entry that is a real picture, computed from the list in both clients (`backgroundPhotoFor` web, `backgroundPhoto(for:)` iOS) — never store it, "next" changes on every reorder and tag filter. **A card is drawn full screen too, not skipped**: `Lightbox.vue` on the web (owner gallery and public share page alike, so pass it `:background-file`), `TextCardSlideView` on iOS via `PresentationPhotoView` and `PhotoDetailView`. A click zooms, for the owner as well as a visitor; editing is a separate control (the tile's pencil and "Edit text" on the web, the long-press menu on iOS) — do not make the tile click mean two different things. **A card is shelved with the chapter it introduces**: `withInheritedDayAndPlace` runs first inside `groupByDayAndRegion` in both clients and hands each card the next picture's capture instant (`next.exif ?? next.uploadedAt`), capture offset and coordinates, on **copies** — writing them onto the row would put a card on the map. A card with nothing after it inherits nothing and keeps the trailing bucket.
- **An album tile is dated by its cover photo** (D85). `AlbumInfo.coverImageDate` is the cover's `exifDateTimeOriginal`, or its `uploadedAt` when there is none, set in `AlbumService.convertToAlbumInfo` from the cover row that method already loads. The cover is the album's first photo by `display_order`, so the date always belongs to the picture on the tile — don't swap in a MIN(date) query. There is no column and no migration. Web reads it in `AlbumCard.vue`, iOS through `Album.coverDate`.
- **Migrations** (Flyway, MariaDB) live in `server/src/main/resources/db/migration/`. Every entity field must match a migrated column or the app fails to start (`ddl-auto: validate`).

## Test caveats

- The **server** suite is green (338 tests, 0 failures, as of 2026-09-07; 11 Docker-gated skips without `-Drun.testcontainers=true`, 1 skip with it). There is no baseline failure to ignore any more — the six stale tests that used to fail were fixed, so any red test is yours. CI (`.github/workflows/server.yml`) runs with the gate open.
- The **frontend** suite is vitest (87 tests, as of 2026-09-07; the six `useAuth` cases fail on a clean checkout too, so that is a baseline failure and not yours): pure utils and composables under jsdom, no component mounting yet. Test files are `src/**/*.test.ts` and are excluded from the app's `tsconfig.json`; `npm run type-check:test` checks them against vitest's types.
- The **iOS** suite is separate and also green (584 test functions / 734 invocations counting parameterised cases, 0 failures, as of 2026-09-07). It is `xcodebuild test`, not Maven — see `ios/Zyncloud/README.md` for the invocation and its two traps (`CODE_SIGNING_ALLOWED=NO` breaks the keychain tests; the `StubServer` suites are process-wide).
- Some IT classes (`ProcessingJobLeaseTest`, `*ProfileContextTest`) are gated by `-Drun.testcontainers=true` because Docker Desktop returns stub responses to docker-java. They run cleanly on a non-Desktop daemon (GitHub's Ubuntu runner, the sandbox's `dind`). Testcontainers is **2.x, version-managed by Spring Boot** (no own BOM or property in the pom; modules are `testcontainers-mariadb`, `testcontainers-minio`, `testcontainers-junit-jupiter`; `MariaDBContainer` lives in `org.testcontainers.mariadb` and has no type parameter). They start their own MariaDB **and MinIO** (`testsupport/TestObjectStorage`) — `BucketBootstrapper` does a `HeadBucket` at startup, so a full context without an S3 endpoint never starts. New `@SpringBootTest` classes need `@ActiveProfiles("api"|"worker")`, `webEnvironment = MOCK` and both containers; copy one of the three. `FileStorageServiceBulkTagIT` is named `*IT`, so Surefire never runs it — not locally, not in CI. Run by name; as of 2026-09-05 its three cases fail with MariaDB's "Record has changed since last read in table 'image_tags'" on the bulk-tag insert, which nobody has looked at yet.

## Single-test syntax

```bash
# Server (Maven Surefire)
./mvnw test -Dtest='ClassName'                  # whole class
./mvnw test -Dtest='ClassName#methodName'       # single method
./mvnw test -Dtest='Pattern*Test'               # glob

# Frontend (vitest, run from frontend/)
npm test                                        # everything
npx vitest run src/utils/__tests__/format.test.ts   # one file
npx vitest run -t "counts calendar days"        # one test by name
```

All other commands (build, dev server, deploy, kubectl) are in `README.md` and `helm/photo-upload/README.md`.
